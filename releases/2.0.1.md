## What changed

Fixes to the machinery around releases. Nothing about how the application stores
or serves your photos changes.

- **The manual-install upgrade steps work now.** They said
  `git fetch --tags && git checkout vX.Y.Z`, but the public repository published no
  tags, so that command failed with `pathspec did not match` for anyone following
  the panel. The release tag is now published alongside each release (and has been
  published for v2.0.0 retroactively), so the version the panel names is a version
  you can actually check out.
- **A release's minimum version is checked, not just mentioned.** If a release
  declares that it requires at least a certain version, that warning now appears
  only when it applies to you, and it names both your version and the one
  required. Previously every install was shown the same notice whatever it ran.
- **An applied database migration may be kept in `db/archive/`.** Previously,
  once one release shipped a migration, the next release had nowhere clean to keep
  the previous one: keeping it blocked the release, deleting it made every upgrade
  report a missing migration, and moving it did both. The runner now counts an
  archived migration as present.
- **The server's config-file path is no longer sent to non-admin accounts.** It is
  server-side detail that only an admin can act on; the panel phrases things
  generically for everyone else.
- `release.json` now carries the `url` its documentation promises, so the panel's
  *Release notes* link appears instead of being silently absent.
- The container entrypoint's comment describes the migration model 2.0.0
  introduced, rather than the one it replaced, and the release-tooling headers no
  longer suggest that maintainer-only scripts ship with the project.

## What this means for your install

Upgrade as usual — this is a code-only release. There is no database migration
and no Android rebuild: the app shell has not changed since v2.0.0, so the APK you
built keeps working.

If you installed a manual checkout and were told to check out a tag that did not
exist, that is fixed here, and v2.0.0's tag has been published as well — either
version is now reachable by tag.

Two things worth knowing about a tag checkout: it leaves you on a detached HEAD,
so the next upgrade is the same two commands with a newer tag; and if your clone
predates this project being re-published, `git pull` will fail with `refusing to
merge unrelated histories` — `git fetch origin && git reset --hard origin/main`
is the way through (keep any local changes first).

## Action required

None beyond upgrading normally:

- **Docker:** `git pull && cd docker && docker compose up -d --build`.
- **Manual:** fetch the tag (or `git pull`), reinstall dependencies,
  `npm run db:status` then `npm run db:init` (which will report nothing to apply),
  and restart the service — or re-run `./setup`, which offers your existing values
  as the defaults.
