## What changed

- **Updates are visible.** Settings → Server → Version & Updates compares this
  install against a release file you configure, and shows the upgrade steps for
  your install shape. The top bar now names the server, shows the release it is
  running, and says *Update: vX.Y.Z* when a newer one exists — clicking it opens
  that panel. It never installs anything by itself and never polls.
- **Database migrations belong to a release.** `db/migrations/<version>-<slug>.sql`
  runs **once**, recorded in `schema_migrations`, instead of every `migrate-*.sql`
  being replayed on every start. `npm run db:status` shows what an install has run
  and what is outstanding; `db:init` applies. A failing migration stops the
  service rather than serving traffic against a half-migrated schema.
- **Release notes are files** (`releases/<version>.md`), and `release.json` — the
  file other installs read — is generated from them, so the panel, the docs and
  the release cannot disagree.
- **Authorised clients are identified by a server-issued token**, not by an IP
  address or a client-generated device id. An install's IP is recorded for the
  admin view but no longer authorises anything.
- **Photos are stored flat**, in `<photos root>/<YYYY-MM>/`, with no per-user
  directory. The library scanner walks the tree recursively, so existing per-user
  layouts keep resolving.
- **`./setup`** — one installer for the whole thing: it detects the machine,
  proposes an install shape (Docker compose or a direct install), asks for the
  values it needs, writes the one configuration file that shape actually uses,
  and can create the database, install dependencies and offer to install the
  services. Re-running it offers your existing values as the defaults.
- The Android app is **built and signed by whoever runs the server**. No APK is
  published by the project; `spore-photos-mobile/scripts/build-apk.sh` builds one
  with your own key (docs/BUILD-APK.md).
- No deployment-specific values anywhere in the code: the release source, the
  server's name, ports, paths and credentials all come from your configuration.

## What this means for your install

This release is mostly about how you run it, not what it stores: the database
schema is unchanged, and no migration ships with it. Upgrade the code, apply the
schema (which is a no-op here), and restart. Take a backup first anyway.

Reinstalling the Android app is required: the app you may have been running was
signed with a key this project no longer ships, and the download it pointed at has
gone. Build your own and your key updates it from then on.

## Action required

- **Android:** uninstall the old app, build your own APK
  (`spore-photos-mobile/scripts/build-apk.sh`, see docs/BUILD-APK.md), install it,
  and set your server address in the app's Settings.
- **Docker installs:** `git pull && cd docker && docker compose up -d --build`.
  (`--build` matters: the image is built from your checkout, not pulled.)
- **Manual installs:** `git pull`, reinstall dependencies, `npm run db:status` to
  see what the release will run, `npm run db:init` to apply it, then restart the
  service — or re-run `./setup`, which offers your existing values as defaults.
- **Optional, once:** point `update.sourceUrl` at the `release.json` of whoever
  you follow, and set `server.siteName` to what you want the app to call your
  server. Without a source, nothing is checked for updates — there is no default
  pointing at anyone else's repository.
- **Before any of it:** back up the database and the photo library (docs/DOCKER.md
  §7, docs/INSTALL.md §10).
